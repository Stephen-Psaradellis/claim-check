Claim Check: app map

A one-page guide to where things live. A snapshot of the code at the commit named at the bottom; it can drift as the code changes.

What the app does

A small-business owner pastes a cold "your website has problems" email and their web address. Claim Check finds each claim in the email, downloads the home page once, and marks every claim True (the problem is really there), False (the page's own code says otherwise) or Can't be checked from outside (rankings, penalties, traffic and the like), each with the evidence it used.

It is one Cloudflare Worker with no dependencies, no keys and no storage. Four pieces do the work:

  • src/claims.js and src/claim-types.js find the claims in the email.
  • src/fetch-site.js downloads the home page (10 s limit, 5 redirects).
  • src/judge.js gives each claim a verdict and its evidence.
  • src/page.js is the whole web page; src/worker.js joins the pieces and answers GET / and POST /check.

One action, end to end: press "Check"

Reference route (three stops)

A route to read in your editor. Search for the anchor in each file.

  1. The request comes in: src/worker.js, search export async function check Splits the work in order: find the claims, fetch the site only if some claim can be checked from the page (needsSite), judge each claim, then add up the verdicts and the notes shown under the table.
  2. Which words count as a claim: src/claim-types.js, search CLAIM_TYPES A plain list of claim types and the phrasings that trigger them. First match per clause wins, so specific types sit above broad ones. A type with a reason is one nobody can check from outside; that reason is shown as its evidence.
  3. The verdict: src/judge.js, search const CHECKS and export async function judge One small check per type, each reading the downloaded page's code (the <title>, the meta tags, the <h1>, the links...) and returning a verdict plus a sentence of evidence that quotes the page.

To change this, start here

  • Catch a new phrasing of an existing claim ("your site is invisible on phones"): add a pattern to that type in src/claim-types.js, then a line in test/claims.test.js.
  • Add a new kind of claim: a new entry in CLAIM_TYPES, a matching function in CHECKS in src/judge.js (or a reason if it can't be checked from outside), a test in test/judge.test.js, and a row in the README's "What it checks" table. The "site is down" and "no H1" types were added exactly this way in the final review.
  • Change the wording people see: verdict sentences live in src/judge.js; headings, labels and the empty/error messages live in src/page.js and src/worker.js.
  • Change the limits (timeout, redirects, how many links are tried): the constants at the top of src/fetch-site.js and MAX_LINKS in src/judge.js.

A practice to reuse

Keep phrasings as data and checks as code, and let a real run find the gaps. The spec chose a fixed claim library over a language model (devpost/spec.md), which kept the build inside one Worker with no keys. In the final review, a run against made-up awkward emails showed two common scare lines ("your site is down", "no H1") that produced no row at all. Because phrasings are data, each fix was one library entry, one small check and two tests (test/claims.test.js, test/judge.test.js), not a redesign. On another project: write the rules a feature recognises as a list you can extend, and before calling it done, try inputs you did not plan for and treat "nothing happened" as a finding.
